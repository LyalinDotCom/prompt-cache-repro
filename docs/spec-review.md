# Review of the supplied benchmark proposals

The two candidate specifications are preserved verbatim under `references/`. They are useful experiment proposals, not a verified description of provider internals or of Theo's unpublished harness. This implementation starts with direct public provider APIs and official SDKs. It measures public usage counters and request histories; native CLI agents, ACP, OAuth/subscription comparisons, private routing telemetry, and server-side cache internals are outside this phase.

## Corrections that affect the experiment

| Candidate claim | Review and implementation decision |
| --- | --- |
| Gemini requires a 6,000-token floor | The current public Gemini 4 Argon minimum is 4,096. Use a large prefix and inspect actual token usage; a character count cannot guarantee a token count. Explicit cache creation is unsupported for Gemini 4 and later. [Google caching guide](https://ai.google.dev/gemini-api/docs/caching) |
| A 2,050-token checkpoint rule, 120-second DRAM eviction floor, hidden minute timestamps, or `EmptyThoughtInjector` explains misses | These are unsupported implementation claims in the supplied text. Do not encode them as provider guarantees or infer them from cache counters. A 2,100-token tolerance is a sensitivity analysis if run separately, not evidence for a checkpoint mechanism. |
| Any replay miss proves routing, metro changes, or KV eviction | Replay reduces client-side prompt variation. A miss still does not identify a server-side cause. Eligibility, service changes, quotas, accounting, and undocumented processing remain possible explanations. Report the observed miss and its evidence without assigning a mechanism. |
| A per-trial nonce guarantees a cold start | A nonce reduces accidental prefix sharing. It cannot flush a public provider cache or prove a first request is cold. Preserve and report first-turn cache reads, and exclude first turns from follow-up hit statistics. |
| All providers should have identical byte payloads | Provider schemas differ. Use identical workload content and deterministic builders within each provider, with stable tools and history ordering. Preserve the built payload and its hash. An SDK request object is not captured wire bytes, and byte identity is not proof of an identical server-rendered prompt. |
| OpenAI cache writes are always zero; all input is either ordinary or read | This is wrong for GPT-6.1 Sol. Responses usage includes `input_tokens_details.cache_write_tokens`; ordinary input is total input minus reads minus writes. Current writes cost 1.25× ordinary input and Sol reads cost 0.05×. Newer models support automatic and explicit breakpoints. [OpenAI caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) |
| Anthropic's `input_tokens` includes cached input | It excludes cache reads and cache creation. Total input is the sum of all three counters; never subtract cache reads from its ordinary input. Sonnet 5.5 currently has a 512-token cache minimum. TTL is measured from request start and refreshed by reuse; response latency consumes part of the reuse window. [Claude caching guide](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) |
| A full hit always means the entire previous token count | This is a declared operational approximation, sensitive to tokenization, cache breakpoints, previous outputs, and provider formatting. Show partial/any hits and token-weighted reuse too. A strict-hit percentage alone cannot establish a token loss or cost percentage. |

Verified public documentation on 2026-10-17. Model IDs, prices, minimum lengths, and API schemas can change. Every report retains its config and SDK versions; rate cards include a source and date. Key/project tier labels are supplied by the operator, not authenticated by the harness.

## Normalization and cost rationale

Normalize each successful request to `input = ordinary + read + write`. For Gemini `generateContent`, use `usageMetadata.promptTokenCount` and `cachedContentTokenCount`; implicit writes have no separately reported billed write category. Do not substitute the Interactions API's `usage.total_cached_tokens` field into a `generateContent` parser: these are different schemas. Keep thinking usage separate so it is not counted twice in output billing. [Google generateContent reference](https://ai.google.dev/api/generate-content)

OpenAI Responses uses `input_tokens` and its details object; a Chat Completions `prompt_tokens_details` fixture tests a different endpoint. Anthropic uses the exclusive three-part split above. Missing, inconsistent, or unsupported counters should remain unknown with a warning rather than become a fabricated cache miss or exact dollar figure. Preserve raw usage for reanalysis.

Actual input cost applies ordinary/read/write rates to their normalized counters. The ideal denominator is a declared approximation to perfect eligible reuse of the previous request, plus new tokens. It must include initial writes and newly cached suffix writes where the provider charges for them; a read-only denominator would make perfect reuse look inefficient. Keep whole-session and follow-up multipliers separate. Output cost is reported separately from input-cache overhead. A model-level rate card is not an invoice: long-context, service-tier, region, batch, and tool charges may require additional pricing logic. Keep benchmark contexts within the verified rate regime or use an explicit appropriate rate card.

## Workloads and interpretation

`replay` repeats the same built request. `append` grows deterministic fixture history. `agent` uses native model tool calls and deterministic tool results; model output and thinking may differ across providers. Preserve native continuation and signature-bearing blocks rather than manufacturing interchangeable signed turns. Fixed fixtures control tool data, not model behavior. If a response cannot be continued safely, mark it and stop that trajectory. `perturb` intentionally changes early context as a negative control; the previous entire input is not an eligible reusable prefix after that change.

The runner waits from response completion to the next request start and records the actual gap. That is an operational idle-time measure, not a direct server cache age. Total elapsed request-to-request time also includes the prior response duration. Request latency here is full response duration, not streaming time to first token. A future SSE arm must define the first meaningful content event and provider-specific reasoning/tool events before comparing TTFT.

Use independent trial nonces, record seeds and actual model IDs, and repeat whole runs. Cell order is shuffled using the recorded config seed. Follow-up turns within one trajectory are correlated: an observation-level confidence interval is descriptive and does not establish independent samples. Compare repeated runs with changed seeds to assess time/order effects. Rate limits, failed requests, minimum-length warnings, invalid continuation, and unavailable counters must remain visible beside the hit metrics.

This phase does not implement cross-session shared-prefix experiments, stateful Interactions versus stateless Gemini comparisons, explicit TTL sweeps, keep-alive controls, or full native-agent stack comparisons. Those need separate controlled arms. A finite run can measure the configured workload's public cache counters and estimated input overhead. It cannot prove a cause of eviction, reproduce an unpublished experiment exactly, or establish real-world agent cost differences from a screenshot.
